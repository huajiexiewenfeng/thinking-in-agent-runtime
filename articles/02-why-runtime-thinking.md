# 为什么要用 Runtime 思维看 Agent

**当前状态：研究骨架**

## 核心问题

为什么模型、Prompt、Skill、Tool Calling 和 Agent Framework 已经存在之后，仍然需要单独研究 Runtime？

## 核心主张

> 模型能力描述“可能做什么”，Runtime 能力决定“能否持续、可靠、可恢复地做成”。

## 文章结构

1. 从一个可以演示的 Agent 到一个可以运行的系统
2. 概率性推理与确定性执行的冲突
3. 长任务、状态和副作用为什么改变了问题性质
4. Skill、Framework、MCP 各自解决什么，又留下什么
5. Runtime 需要保证的最小不变量
6. 企业场景为什么更依赖权限、审计、恢复和 Eval
7. Runtime 思维不适用或不值得引入的场景

## 需要核实的证据

- 一次真实长任务中断或恢复案例
- 一次重复 Tool Call 导致副作用的案例
- 一次知识读取缺少来源导致错误判断的案例
- 一个只有 Framework、没有持久状态与恢复机制的对照

## 实践映射

- 第 13 篇 `llm-wiki-runtime` 实践将验证确定性知识访问。
- 第 14 篇 Loop Runtime 实践将验证持续执行边界。
- 第 15 篇 State Runtime 实践将验证恢复与幂等。

## 本章不提前下的结论

本章不会把所有 Agent 应用都升级成复杂 Runtime。只有当任务出现持续执行、状态、工具副作用、跨会话知识、治理或评测需求时，Runtime 思维才产生足够价值。
